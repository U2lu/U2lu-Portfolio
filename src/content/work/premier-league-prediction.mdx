## The honest version of the problem

Football has three outcomes and the bookmakers are already very good at them. So the interesting question here is not “can it predict football”. It is: how much signal is actually in six form features, and how would I know if they were worth anything?

That second half is the project. Anyone can fit a model and print an accuracy figure.

## The data

Fixtures from API-Football, ten seasons of the Premier League. The collector is resumable by design: it reads the CSV it already has, works out which seasons are missing, and only fetches those. It de-duplicates on `fixture_id`, keeps only matches that finished with a real score, sorts them chronologically, and raises on an API error rather than writing half a season.

That last detail is not fussiness. A dataset silently missing September is a dataset that will produce a confident, wrong answer later.

## Features

Six numbers per fixture: the rolling five-match average of goals scored, goals conceded and points — for the home team and the away team.

The one decision that matters is `shift(1)`. Each average is computed from the matches *before* the fixture, never including it. Without that shift, the row contains the result it is trying to predict and the model scores beautifully on paper while knowing nothing. Teams with no history get zeros, which is the honest encoding: a newly promoted side in August has no form, and inventing some would leak the season.

The feature builder validates as it goes — required columns present, no duplicate fixtures, `1:1` merges, no team twice on the same date, and the row count unchanged at the end. It would rather fail loudly than train on a broken table.

## Split and baseline

Chronological, not random. Train on seasons up to 2022, test on 2023 onward. A random split on time-ordered data lets the model train on the future, which is a very easy way to look clever.

Then a baseline that always predicts the most common outcome in training. Home wins are about 43% of matches, so a model that cannot beat “always home win” has learned nothing — and accuracy alone would hide that, because the baseline itself scores respectably.

So evaluation reports balanced accuracy, macro F1 and log loss alongside it. Log loss is the one that matters for a product: it punishes being confidently wrong, which is exactly the failure that would make a prediction service worthless.

## Two models, on purpose

A Random Forest and an XGBoost, chosen to disagree. Four hundred trees at depth 8 with balanced class weights, against four hundred boosted rounds at depth 4 and a 0.04 learning rate. Both save their feature list and label mapping next to the model file, so a prediction cannot silently use a different column order than training did.

760 matches from 2023 and 2024, none of them seen during training.

**It beats the baseline, and not by accident.** Accuracy is the least interesting column here. The baseline's 43.4% is not a skill score — it is the base rate. 330 of the 760 test matches were home wins, so “always home” gets 43% for free.

Balanced accuracy is the column that separates them. 0.333 is exactly what a model that never predicts a draw or an away win looks like; 0.437 is a model that is genuinely splitting three ways. Macro F1 nearly doubles, 0.20 to 0.43. The Random Forest is not just leaning harder on the favourite.

**48% is still wrong more often than right.** This is not a betting product — at 48% it would lose money, and I would say that to anyone who asked. What it shows is narrower and true: six form features carry a small, measurable amount of signal about a match result.

**The Random Forest wins, which I did not expect.** XGBoost is behind on all four metrics. Boosting is not automatically better — with 3,040 training rows and six features, a bagged forest with balanced class weights has more to regularise against than 400 boosted rounds do.

**Draws are where both of them fail.**

XGBoost finds 5 of the 175 draws in the test set. The Random Forest — the weaker of the two on home and away wins — finds 31. That is not a bug in the code; it is what a global log-loss objective does when one class is the least separable, buying accuracy by abandoning that class entirely. `class_weight="balanced"` is the reason the forest keeps looking for draws at all, and the clearest sign the weighting was the right call.

**And this is the number worth keeping.** A model that outputs the training base rates for every single match would score a log loss equal to the entropy of the class distribution — roughly 1.067 on this test set. The Random Forest scores 1.058.

Its probabilities are within one percent of saying “home win, 43%” every time.

So the model has learned which way to lean, and has not learned how confident to be. A screen showing “63% home win” from this model would be lying to whoever read it. That gap is the real argument for not shipping probabilities yet — and XGBoost's 1.069, worse than the constant, is the same failure with a smaller footprint.

## Where it actually stands

The pipeline runs end to end: collect, prepare, train, evaluate, save, and the numbers above come out of it. Tuning is not finished.

Two seasons is also a small test set. On 760 matches, three or four points of that gap could be fixture-list luck rather than signal — the balanced-accuracy jump is the part that is much harder to explain away.

Those numbers are on this page because I typed them in from a terminal, which is the one thing on this list a JSON file would fix.

There is no service yet, either. `api.py` in the repo is a one-shot script that fetches one season and prints its first fixture. It is a data probe, not an API, despite the filename.

## What’s next

- **Persist the evaluation.** Write each run's metrics to JSON alongside its hyperparameters, so the table above regenerates instead of being typed in.
- **Close the calibration gap before showing any probability.** The forest ranks outcomes better than it estimates their likelihood. Recalibrate, or ship a lean-only interface — never a percentage it cannot defend.
- **Push past six rolling averages.** Elo, expected goals, days of rest and home/away splits are the obvious next inputs. The calibration result says the next gain has to come from somewhere other than form.
- **Move the model files out of git.** They are 7 MB and 1.9 MB, they change on every run, and releases or object storage are the right home for them.
- **Retire the earlier pipeline.** There are two collectors and two match CSVs in the tree; one is the live pipeline and the other is a draft. Removing the draft makes the repo read the way the model is built.
- **Test the shift.** One test asserting that no row's features are derived from that row's own result would protect the single assumption the whole model rests on.
